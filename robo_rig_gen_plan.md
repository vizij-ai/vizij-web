# Robot Rig Graph Generation Plan

Note: This plan is left was work todo, and is subject to change based on integration of work being done that will modify the rig graph.

## Current Workflow Summary

### Low-level rig definitions (`@vizij/config`)
- **Files:** `packages/@vizij/config/src/rigs.ts`, `low_rig.ts`, `models.ts`, `expression.ts`, `viseme.ts`.
- **Low-level rigs** (e.g. `HugoLowLevelRig`, `QuoriLowLevelRig`) are hand-written `LowLevelRigDefinition` objects. Each channel lists tracks (`pos`, `rot`, `scale`, `morph`, etc.), optional axis filters, and optional `mapFunc` helpers. The `shapeKey` and track name determine an implicit search key (e.g. `"Mouth translation"`, `"Plane Key 1"`).
- **`VizijLowRig`** consumes the definition and a set of renderer animatables. During construction it walks every `(channel, track)` pair, builds the search key, and scans `loadedAnimatables` for a matching `anim.name`. If found, it stores a `VizijLowRigTrackMap` entry pointing at that animatable’s ID and default value.
- **Application step:** `VizijLowRig.apply(pose)` receives a `Pose` created against the stable `VizijStandardControlVector`. For every mapped track it:
  - Extracts the current rig channel values from the pose.
  - Runs `mapFunc` if provided (defaults add/multiply against the stored base value).
  - Invokes the renderer store’s `setValue(animatableId, namespace, value)` to push the new pose into the world.
- **Standard rig:** `VizijStandardControlVector` is the canonical channel/track list. Expressions (`expression.ts`) and visemes (`viseme.ts`) are hard-coded `Pose` instances built with that vector, ensuring author tools always output the same channel names/tracks the low-level rigs expect.

### Rig instantiation (`@vizij/rig`)
- **`useModelLoader` / `useRiggedModelLoader`** (packages/@vizij/rig/src/useModelLoader.ts):
  - Load a `.glb` via `loadGLTF`, optionally seed initial animatable values.
  - Instantiate a `VizijLowRig` with the low-level definition and the loaded animatables.
  - Expose the `VizijLowRig` instance so downstream code can call `apply(pose)`.
- The loader assumes the low-level rig will find its animatables purely by name; nothing is persisted about the mapping.

### Usage in product surfaces
- **`demo-render-no-rig` app:**
  - Imports the static low-level rig definitions (see `apps/demo-render-no-rig/src/data/faces.ts`).
  - `buildRigGraph` (apps/demo-render-no-rig/src/rig/rigGraphGenerator.ts) mirrors the `VizijLowRig` matching logic: it flattens the `AnimatableList`, builds the same search keys, and constructs a node graph that connects rig inputs (`rig/<face>/<channel>/<track>/<axis>`) to renderer animatables.
  - The generated graph is rendered in the UI and can be exported, but the canonical data still lives in TypeScript definitions – edits in the UI are not persisted back to config.
- **Website demos (`VizijVisemeDemo`, `VizijExpressionsDemo`):**
  - Call `useRiggedModelLoader(Hugo, HugoLowLevelRig)` to load the model and instantiate a `VizijLowRig`.
  - Build poses from the standard control vector (expressions + visemes) and feed them through `useBlendTree`, which eventually calls `rig.apply(pose)` for each active rig.
  - Entire flow depends on the low-level rig having successfully auto-bound to renderer animatables by the name heuristics.

### Key Observations
- Low-level rig → animatable mapping is implicit and brittle (string comparisons, scale helpers baked as JS functions).
- There is no persisted artifact that records which animatable a given standard-channel drive controls – every runtime recomputes it.
- Authoring new robots or modifying GLBs requires TypeScript edits to `rigs.ts` and, frequently, corresponding changes to naming inside the model.
- The autogenerated graph in the demo duplicates logic already present in `VizijLowRig`; discrepancies between the two can create confusing divergences.

## Goals for the New Process
1. **Keep the standard rig stable** – `VizijStandardControlVector` remains the canonical list of channels/tracks. Expressions, visemes, and author tooling continue to target this schema.
2. **Move mapping data out of hard-coded TypeScript** – instead of inventing search keys at runtime, store explicit connections between standard rig tracks and renderer animatables in a graph artifact.
3. **Allow ergonomic authoring** – provide tooling (graph editor / wizard) so robot builders can create or tweak the mapping without writing code. Auto-suggestions should bootstrap from current heuristics but remain editable.
4. **Support dynamic animatables** – the mapping layer must tolerate different renderer exports (extra morphs, alternative names) without forcing code changes; users should be able to bind new animatables on the fly and persist the result.
5. **Reuse graphs at runtime** – loader code should consume the stored mapping and drive animatables directly, avoiding a second name lookup step.

## Proposed Direction: Robot Rig Graph Mapping

### Data model
- Introduce a `RobotRigGraph` asset (JSON or declarative TypeScript) that captures:
  - **Inputs:** canonical paths derived from `VizijStandardControlVector` (e.g. `standard://mouth.pos.x` or similar) with metadata (value type, range).
  - **Nodes:** light-weight graph nodes (add, multiply, constants, axis joins) similar to what `buildRigGraph` currently produces.
  - **Outputs:** explicit bindings from node outputs to renderer animatable IDs or stable lookup keys (`animatable.name` + optional namespace).
  - **Metadata:** robot/face identifier, versioning, optional heuristics for regenerating suggestions when animatables change.
- Store graphs alongside robot assets (e.g. `packages/@vizij/config/rig-graphs/<robot>.json`).

### Authoring workflow
- Extend `demo-render-no-rig`’s rig editor to act as the canonical authoring tool:
  - When a GLB loads, pre-populate the graph using current heuristics (`buildRigGraph`).
  - Allow users to re-route outputs, add math nodes, or bind additional animatables discovered at runtime.
  - Provide diffing/highlight to show unmapped animatables or unconsumed standard channels.
  - Offer “export graph” that writes into the new `RobotRigGraph` format (ideally committed to the repo).
- Optionally build a CLI that converts existing low-level definitions (`rigs.ts` + `mapFunc`) into initial graphs to avoid manual rework.
- Encourage asset authors to ship both the GLB and its graph; the low-level TypeScript definitions become reference fixtures rather than runtime dependencies.

### Runtime integration
- Update `useRiggedModelLoader` to:
  1. Load the GLB and collect animatables as it does today.
  2. Load the corresponding `RobotRigGraph`.
  3. Build a runtime evaluator (`RobotRigRunner`) that:
     - Binds graph outputs to animatable IDs present in the loaded model.
     - Substitutes defaults when the graph references an animatable that is missing (surface diagnostics).
     - Executes the graph when `apply(pose)` is called, using the pose values as graph inputs.
- `VizijLowRig` can either be refactored into this runner or wrap the runner internally. The key change is that the mapping no longer depends on constructing search keys; it reads them from the graph.
- Ensure website demos and orchestrator tooling request the graph-backed runner. Existing APIs (`rig.apply(pose)`) should stay stable to avoid rippling changes outward.

### Handling dynamic animatables
- When a GLB exposes animatables not referenced in the stored graph, surface them in the authoring tool and let users bind them interactively.
- Consider supporting named groups or tags within the graph so multiple animatables can be targeted by a single standard channel (e.g. twin eyelid morphs).
- Provide fallbacks (e.g. identity mapping) when no graph is found – perhaps re-run the heuristic matching and prompt the user to save the result.

## Implementation Plan

1. **Archive current behaviour**
   - Document existing low-level rig behaviour (this report) and keep definitions as reference fixtures for regression tests.
   - Extract automated tests that verify the heuristic mapping still works (use Hugo/Quori as baselines).

2. **Design the `RobotRigGraph` schema**
   - Finalise JSON schema (inputs, nodes, outputs, metadata).
   - Define a runtime evaluator interface (`RobotRigRunner.apply(pose)`).
   - Describe how animatable lookups are resolved (prefer ID when known, fall back to name).

3. **Authoring tooling updates**
   - Refactor `buildRigGraph` to emit the new schema (without serialising to runtime structures).
   - Add save/load support in demo-render-no-rig for the graph files.
   - Implement validation (missing animatables, mismatched value kinds).
   - Optionally create a conversion script that generates initial graphs from `HugoLowLevelRig`/`QuoriLowLevelRig`.

4. **Runtime integration**
   - Implement `RobotRigRunner` capable of executing the graph, including support for map functions (scale/add) currently expressed in code.
   - Update `useRiggedModelLoader` to instantiate the runner from a graph if available, falling back to existing `VizijLowRig` until all assets migrate.
   - Adapt website demos and any downstream consumers to prefer the graph-backed runner, keeping the public API stable.

5. **Migration**
   - Generate graphs for Hugo and Quori; ensure both the demo and website continue to function.
   - Deprecate the TypeScript low-level definitions once confidence is high (retain them for test fixtures or as fallbacks during transition).
   - Provide guidance for partners on how to author graphs for new robots (update README / docs).

6. **Future enhancements**
   - Integrate orchestrator “robot rig graph” authoring directly into production tooling so teams can manage mappings without touching the demo app.
   - Explore graph sharing/versioning (e.g. embed graph references in GLB metadata or host in asset pipeline).
   - Investigate live graph reloading to support hot-editing while a simulation runs.

By anchoring the mapping data in a dedicated graph artifact and offering tooling to author it, we retain the stability of the standard rig while giving teams the flexibility to bind arbitrary animatables without code changes.
